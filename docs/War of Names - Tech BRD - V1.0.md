2) مبادئ تنفيذية أساسية
2.1 مبادئ معمارية

الواجهة الأمامية والخلفية منفصلتان بالكامل.

كل منطق الأعمال الحاسم ينفذ في الـ Backend فقط.

الـ Frontend مسؤول عن العرض والتفاعل والتحقق الأولي فقط.

قاعدة البيانات تمثل المصدر المرجعي للحالة.

جميع القواعد المتغيرة يجب أن تكون قابلة للإدارة عبر إعدادات منظمة.

جميع المحركات الأساسية يجب أن تبنى كإطارات قابلة لإعادة الاستخدام، لا كحلول مخصصة لحالة واحدة.

2.2 مبادئ ضد التعقيد

لا منطق مكرر بين أكثر من طبقة.

لا features ثابتة إذا المطلوب framework عام.

لا generalized engine مبالغ فيه يفوق الحاجة الحالية.

لا سكربتات منفصلة لكل عنصر أو لكل حالة.

لا تحديث مباشر للحالة دون المرور عبر طبقة الأعمال والسجل المناسب.

لا coupling غير ضروري بين الـ Frontend والـ Backend.

2.3 مبادئ تشغيلية

كل حدث مؤثر يجب أن يكون قابلاً للتتبع.

كل تغيير إداري يجب أن يكون بسبب وسجل.

كل عملية مالية يجب أن تمر عبر Ledger.

كل عملية منطقية/إدارية يجب أن تمر عبر Audit Trail.

كل حالة حساسة يجب أن يكون لها تمثيل واضح في الواجهة.

13) قواعد الواجهة الأمامية
13.1 عامة

React/Vite

RTL-first

mobile-responsive بدرجة عالية

no business-critical logic in frontend

use typed contracts where possible

handle loading / empty / error states properly

13.2 قواعد UX

كل عملية حساسة لها confirm step

كل شاشة تعرض ما هو مهم فقط

لا ازدحام بصري

لا تعقيد في خطوات اللاعب

عرض الحالات بوضوح: مفلس، محمي، غير مؤهل، منتهي، مغلق

13.3 قواعد state management

حالات الواجهة يجب أن تكون واضحة

لا duplication للبيانات نفسها في أكثر من مكان بلا داعٍ

أي حدث يغير الحالة المركزية يجب أن ينعكس بشكل موحد

14) قواعد الخلفية Backend
14.1 عامة

Python API

business rules enforced server-side

clear service boundaries

auditability

deterministic processing

documented APIs

14.2 قواعد المنطق

لا تحديث مباشر للنقاط أو الحالات خارج المحركات

الهجوم يمر عبر Attack Engine

الشراء يمر عبر Store/Item Engine

النقاط تمر عبر Ledger

التعديل الإداري يسجل دائمًا

14.3 قواعد الأخطاء

رسائل أخطاء وظيفية واضحة

فصل أخطاء validation عن permission عن business rules عن server failures

لا كشف معلومات داخلية حساسة في رسائل المستخدم
